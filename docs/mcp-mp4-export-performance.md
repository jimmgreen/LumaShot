# MP4 导出耗时与阶段进度优化

日期：2026-09-17

## 用户目标与范围

用户反馈前20%特别慢，随后很快结束；进一步确认同时优化实际耗时和进度反馈。仅改 MP4 导出、导出状态展示及相关测试。保留此前贴图滚轮优化、引导线修复和六色预设。未读取个人视频、偏好或剪贴板作为测试素材；未运行安装器。

## 复现与原因

使用 tests/mp4_codec_probe.cpp 生成1920×1080、30fps、600帧/20秒合成录制，包含文字、渐变、滚动、运动棋盘和AAC同步脉冲。旧版生产 ExportMp4ToFile 完整耗时39,218ms。

基线观察器包含约160ms外层启动偏移：20%出现在33,163ms，25%在35,799ms，33%在39,364ms，随即99%、100%。与用户描述一致。

源码中首轮AV1编码只分到2–25%，其校验到33%；另外两次可能根本不会执行的重试仍各占31%的区间。首轮成功即跳到99%保存，故进度与已执行工作不对应。

SSIM校验使用 settb=AVTB,setpts=N 以逐帧对齐，输出时间单位因此是微秒中的帧序号，不能再除以原视频时长计算完成比例。这导致校验过程中几乎不报告进展。

## 实现

- 新增可选 Mp4StageCallback，报告检查媒体、压缩、画质校验、写入和完成，百分比明确是当前阶段的完成比例；不能量化的检查/写入使用-1，显示省略号而非虚构数字。
- 工作线程将阶段标签及阶段百分比在同一mutex内发布到PanelState；GUI不再使用为三轮重试预留的旧总进度。重试显示第几次压缩，阶段切换时百分比可重新开始，不伪装成总耗时估算。
- 旧 int 回调保留单调性以兼容既有调用者；测试日志同时包含旧回调和新阶段回调，应以 stage/percent 字段判断新GUI显示。只有原子保存完成后才发出 Complete。
- 编码按实际 out_time_us，画质校验按实际 frame/预期总帧数报告。没有用计时器自行推进进度。
- 首轮SVT-AV1改为preset 8，CRF仍36；不降低分辨率、帧率或画质验收标准。高质量重试保持preset 6/CRF28，H.264后备仍为slow/CRF18。
- 1080p及以下最多4个AV1并行单元，超过1080p保留原2个；同时不超过活动处理器数。保留低于正常优先级、3GiB作业限制、超时、进程树取消和原文件安全回退。
- 全片帧数/时间戳、尺寸、时长、AAC压缩数据哈希检查不变。SSIM仍要求均值>=0.99，所有帧>=0.96，低于0.98的帧不超过1%；候选只有通过检查且体积小于原录制才会采用。

## 测量与取舍

同一合成1080p素材、同机生产导出路径，单轮测量，未隔离后台系统负载；不承诺所有视频固定加速比例。

| 指标 | 旧版 | 最终方案 |
|---|---:|---:|
| 全流程 | 39,218ms | 28,719ms |
| 输出编码 | AV1 | AV1 |
| 原录制字节数 | 3,637,664 | 3,637,664 |
| 输出字节数 | 681,374 | 770,273 |

完整耗时减少约26.8%。新的输出比旧版大约13.0%，但比原录制小约78.8%；这是编码速度与压缩效率之间的明确取舍，不宣称无损或像素一致。

独立FFmpeg参数实验：preset6/lp4编码26,830ms，输出681,374字节；preset8/lp4编码19,140ms，输出770,273字节。后者600帧SSIM均值0.999029843，最小0.998001，低于0.98的帧为0。该实验以常规优先级运行，不能把它的时间直接当作GUI生产导出时间。

只增加并行度的中间生产版本实测40,172ms，未显示总耗时改善，因此没有把该实验包装成成功；最终选择经生产路径验证的更快首轮preset。

4K检查：合成1080p片段缩放为3840×2160、4秒，并非个人录像。中间版本在4个并行单元下AV1两轮未完成，安全回退H.264；未捕获退出码，不把内存限制作为已确认的唯一失败原因。恢复高分辨率原有2个并行单元后，首轮AV1成功、完整校验通过，17,125ms完成，1,399,714字节变为390,284字节。此项验证边界行为，不是4K前后性能对照。
