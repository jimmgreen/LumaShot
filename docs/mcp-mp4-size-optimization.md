## 原因与实现

当前实时录制偏向质量，保留较大的 H.264 缓存是为了不把复杂离线压缩塞进实时采集。本轮不改动实时编码质量，而改进保存阶段。

旧保存流程使用 x264 slow / CRF18，但要求平均 SSIM ≥0.998、每帧 ≥0.99。新视频的自然运动样段在正确逐帧对齐后约为 0.992981，因旧门槛退回原文件。另有两个独立的变帧时间问题：只设置 fps_mode passthrough 仍会量化编码时间基；Media Foundation 估算的平均帧率分数在重封装后并非稳定不变量。过滤器按近似时间戳配对也可能错取相邻帧。

src/recording/mp4_export.cpp 的新流程：

1. SVT-AV1 preset6 / CRF36 / tune0 / lp2 / lookahead16；未通过则尝试更高质量的 CRF28，再尝试兼容的 x264 slow / CRF18。
2. 同时设置 fps_mode passthrough 和 enc_time_base demux，保留实际采集时间；以所有帧时间和帧数验证时间轴，不再要求 MF 估算帧率分数完全相等。
3. 候选必须更小、编码类型正确，并通过原生元数据、逐帧时间、音轨及音频包哈希检查。
4. SSIM 在相同时间基下按解码帧序号比较；日志帧数必须与输入一致。
5. 最终画质规则：全片平均 SSIM ≥0.99，至少 99% 的帧 ≥0.98，任一帧 ≥0.96。三项分别限制整体下降、持续局部下降与严重坏帧。
6. 后台独立进程、低优先级、3 GiB 单进程提交内存限制、每个进程 15 分钟时限；取消会停止作业且不覆盖目标。所有候选失败或变大时保留原片，并明确报告未压缩。

src/recording/worker.cpp 的非模态提示现在显示实际采用的编码和缩小比例，或者“未压缩，已保留原文件”。原来的 GIF 提示和快速录制预览保持；预览使用原始 H.264 缓存，而非重新打开 AV1 导出文件。

## 实验过程与取舍

最初的 12 秒样段测试用原始时间戳驱动帧同步，产生相邻帧错配和末帧重复，曾报告 720 帧。该组原始 SSIM/VMAF 不作为最终质量结论。修正为整数帧序号后，样段实际对应 719 帧；记录保留在 build/mp4-size/index-ssim-results.json。

修正后 AV1 VQ 样段：CRF36 为 6,125,022 字节，平均 SSIM 0.989299、最低 0.984113，隔帧采样 VMAF 94.513684；CRF40 为 4,800,056 字节，平均 SSIM 0.987014，VMAF 93.465810。更激进的 CRF40 没有作为默认值。

完整新视频的 CRF36 候选只有 11/3864 帧低于初步的单帧 0.975 门槛，整体均值为 0.991106。已检查其最差帧（索引3154）及样段最差帧（索引62）的纹理和文字区域：有轻微软化，抽查中未见明显严重的新乱码或块状破损。这不等于已经完整主观播放验收全部内容。

初步一刀切门槛因此触发 CRF28 重试，得到 47,714,194 字节文件，双次编码与校验共 664.9 秒。最终改用上述三重质量规则；复用之前由真实导出链生成的 30,209,709 字节 CRF36 候选，使用当前生产 Inspect、Same、Run、Quality 与 SaveOutput 重新完整校验并提交，没有为了新规则重复编码一次。这个复验不冒充新的完整编码耗时。

旧视频的 CRF36 从实际导出入口正常完成，耗时 195.56 秒；该候选也通过最终规则复验。因此，本机一分钟左右素材的 AV1 软件导出可能需要数分钟，不承诺固定速度。用户选择了体积优先；采集停止后的快速预览不等待这次离线压缩。
